## 1. 도달해야 할 사용자 행동

사용자가 자기 프로젝트를 만들거나 열고, 실제 FreeCAD FEM 파일을 선택한다. 네이티브 프로그램에서 형상·메시·재료·조건을 편집하고 CalculiX 입력을 작성한다. 워크벤치는 그 입력을 받아 계산하고, 실제 결과 파일을 ParaView로 열며, 같은 실행의 설정·로그·결과를 전문가에게 전달한다. 사용자는 제안을 검토해 적용하거나 네이티브 프로그램에서 변경하고 다시 계산한다. 저장 후 재열면 프로젝트·실행 결과·토론이 유지되고 자동 계산이나 LLM 호출은 일어나지 않는다.

초기 사용자 모델 경로는 CalculiX 하나에 집중한다. 이 경로의 네이티브 입력 수용 범위를 보조 변환기의 요소·재료 지원표로 제한하지 않는다. 압력·자중·마찰 접촉·비선형 재료·사면체·육면체·셸은 1단계 종료 조건을 확인할 입력 범위다. 네이티브 작성기에서 특정 조합을 지원하지 못하면 그 제한과 가능한 원 덱 경로를 정확히 기록한다. 불가능한 조건을 생략해서 통과시키지 않는다.

Windows 실화면은 기존 사용자 지시대로 보류한다. Linux의 비시각적 연결과 자동 검증을 먼저 진행하고, Windows 미실시를 이유로 해당 작업을 멈추거나 전체 GUI 완료를 선언하지 않는다.

## 3. 목표 모듈 경계와 최소 데이터 계약

아래 새 경로 이름은 구현 제안이다. 이미 같은 책임을 가진 코드가 추가됐다면 중복 모듈을 만들지 말고 재사용한다. 공통 형식에 전체 FE 입력을 다시 담지 않는다.

| 책임 | 위치 | 외부에 제공할 계약 |
|---|---|---|
| 프로그램 탐색·설치 정보·명령 정의 | `caelab/connections.py` | 환경변수 명시값 → 설치 레지스트리 → PATH 순서, 실제 경로·실행 환경·발견 이유 |
| 프로젝트와 파일 관계 | `caelab/project.py` 또는 작은 `caelab/project/` | 프로그램 노드, 입출력 참조, 연결, 선택 실행, 저장/읽기 |
| 사용자 명령의 단일 입구 | `caelab/workbench.py` | 프로젝트 열기/저장, 네이티브 열기, 입력 등록, 제출/취소, 결과 열기, 토론·제안 적용 |
| 프로세스와 상태 소유 | `caelab/jobs.py` | 비동기 제출, 상태 조회, 취소, stdout/stderr, 종료·판독 상태, 저장·복구 |
| 네이티브 파일별 동작 | `caelab/native/` | FreeCAD 문서 열기/원 덱 교환, CalculiX 원 덱 실행, 결과 교환, ParaView 열기 |
| 보조 변환 | 기존 `caelab/solvers` | 내부 모델을 덱으로 변환하는 명시적 보조 실행. 네이티브 원 덱을 여기로 강제하지 않음 |
| 결과와 토론 근거 | `caelab/result_summary.py`, `caelab/assist` | 실행·입력 개정·솔버·단위·프레임·파일 출처를 가진 요약과 대화 |
| GUI | `apps/workbench_qt` | 서비스 상태 표시와 사용자 명령 전달. 직접 subprocess, 경로 조작, 모델 변경 로직을 소유하지 않음 |

최소 프로젝트 문서는 다음 정보만 소유한다.

- 프로그램 노드의 식별자, 역할, 연결된 네이티브 문서·입력·출력 참조.
- 연결의 출발 출력과 도착 입력. 선만 그려 놓은 연결은 저장하지 않는다.
- 파일 경로, 프로젝트 내부/외부 여부, 자동으로 얻은 개정 식별 정보, 단위 선언과 그 출처.
- 실행별 입력 스냅샷 참조, 작업 상태, 결과 파일, stdout/stderr, 판독 상태, 선택 실행.
- 실행에 연결된 토론·제안·적용 이력과 사용자의 제약.

제안하는 프로젝트 배치는 `project.json`, `runs/<run-id>/`, `discussions/`다. 이름 자체는 고정 요구가 아니다. 외부 CAD를 무조건 복사하지 않되, 계산 시점 입력과 현재 편집 중인 원본을 혼동하지 않아야 한다. include 파일을 쓰는 덱은 필요한 참조를 함께 보존한다. 임의 경로의 원본을 실행 결과로 덮어쓰지 않는다.

상태는 다음을 구별한다: 프로그램이 설치됨, 입력이 준비됨, 실행 중, 프로세스 종료, 결과 판독 완료, 상위 입력 변경으로 결과가 오래됨, 실패, 취소. 설치됐다는 이유로 결과를 '최신'이라고 표시하지 않는다.

각 단위는 사용자 행동을 바꾸는 PR로 구성한다. 계획·상태 문서만 갱신하는 PR을 제품 진척으로 세지 않는다. 필요한 회귀 검사는 수정과 함께 작성하되, 구현을 그대로 따라 하는 테스트를 늘리지 않는다.

### P1. 잘못된 성공과 조건 누락 차단

대상: `caelab/workbench.py`, `jobs.py`, `solvers/base.py`, `solvers/calculix.py`, `numerical/model_binding.py`, `result_summary.py`, `assist/knowledge.py`.

수정 내용:

1. 보조 변환 실행 직전에 입력·지원 검사를 수행한다. 오류가 있으면 덱 생성과 프로세스 호출을 하지 않고 객체 위치를 가진 오류를 반환한다.
2. 단계·재료·하중·접촉·단면·초기조건·출력 요청·증분 옵션 중 실제로 쓰지 않는 항목을 조사하고, 의미를 잃는 입력은 거부한다. 새 물리 기능을 구현하는 작업으로 확대하지 않는다.
3. 결과 판독에 필요한 블록·유효 레코드·프레임 존재를 확인한다. 누락 값은 null/미확인으로 표현하고 0으로 대체하지 않는다. 기존 정상 판독은 유지한다.
4. 실행·판독 예외가 발생해도 작업을 failed로 끝내고 원인을 보존한다. 전체 로그를 실행 폴더에 저장하고 화면에는 꼬리를 보여 준다.
5. ModelEvaluator가 딕셔너리 결과의 실패·취소·부분 실패를 보존하게 한다.
6. 요약의 solver_id와 단위를 실제 결과에서 얻는다. 단위를 알 수 없으면 사용자 선언을 받으며 SI로 추정하지 않는다.
7. RAG 검색의 솔버 제한을 유지한다. 해당 자료 없음과 색인/서비스 오류를 구분해 반환한다.

완료 검사:

- contact/modal 등 미지원 입력에서는 프로세스가 호출되지 않는다. 지원하는 기존 입력의 덱은 의미가 유지된다.
- 빈/손상된 FRD, 요청 필드 누락, 시간 초과, 존재하지 않는 실행 파일이 성공·0 또는 running 고착이 되지 않는다.
- 실패한 딕셔너리 응답이 최적화의 유효 후보로 채택되지 않는다.
- Code_Aster 요약이 CalculiX로 바뀌지 않고, Code_Aster 자료가 없을 때 CalculiX 지식으로 대체되지 않는다.

검사 위치: 기존 `tests/test_calculix_converter.py`, `test_model_and_validate.py`, `test_numerical_model_binding.py`, `test_connections_summary.py`, `test_assist_rag.py`를 중심으로 추가한다. 단위 테스트의 프로세스 모의와 실제 솔버 실행을 보고에서 구분한다.

### P4. 네이티브 계산과 실행 관리

대상: `caelab/native/`, `jobs.py`, `workbench.py`, 결과 판독·교환 코드, GUI 실행 상태 연결.

수정 내용:

1. FreeCAD FEM에서 작성한 실제 덱을 직접 실행한다. 첫 연결에서 사용자가 네이티브 프로그램의 작성 버튼을 누르는 경우도 프로젝트에서 파일·개정·작성 완료 상태를 확인한다. 원 파일을 편집한 뒤 이전 덱을 최신으로 오인하지 않는다.
2. 기존 FreeCAD 작성·읽기 및 CalculiX 실행·FRD 변환 코드를 조사하여 재사용한다. 자체 재료·요소·조건 작성기를 늘리지 않는다. 기존 자산의 import 의존성·라이선스·특정 사례 가정을 확인한다.
3. 원 덱과 include 의존 파일을 실행별 폴더에 보존하고 재작성 없이 계산한다. 입력의 단위는 별도 선언과 출처로 보존한다.
4. JobManager가 프로세스·로그·상태·취소를 소유하도록 비동기로 실행한다. 사용자가 시작하지 않은 외부 프로세스를 종료하지 않는다. 실행 중 앱이 종료되면 다음 열기에서 interrupted로 복원하며 자동 재실행하지 않는다.
5. `runs/<run-id>`에 작업과 입력/결과 참조를 기록한다. 동일 프로젝트의 동시 제어 정책을 명시한다. 기존 JobManager의 잠금·취소·작업 기록 중 필요한 기능을 이식한다.
6. 결과 판독은 원본의 프레임·집합·성분을 구분하고, ParaView에서 열 교환 파일을 만든다. 기존 FRD→VTU 경로를 우선 재사용하고 노드/요소/필드 대응을 확인한다.

완료 검사:

- 동일한 네이티브 덱의 직접 CCX 실행과 워크벤치 실행에서 물리 입력이 동일하다. 실행별 경로 정리 외에 모델 의미를 바꾸지 않는다.
- 실제 실행 환경이 있으면 완료·실패·취소를 확인하고, GUI 이벤트 처리가 계속 가능하다.
- 없는 실행 파일, 비정상 종료, 시간 초과, 판독 실패, 중단 후 재열기에 모두 명확한 종료/복구 상태가 남는다.
- 결과 요약은 실제 파일의 알려진 값과 대조한다. 같은 판독기를 두 번 호출한 일치만으로 정확성을 주장하지 않는다.
- 네이티브 덱이 보조 변환기의 지원표 때문에 거부되지 않는다.

### P5. 같은 결과를 ParaView와 전문가에게 전달

- 실패 결과도 로그와 실패 이유를 근거로 논의할 수 있다. 값이 없을 때 계산값을 만들어 채우지 않는다.

### P7. 1단계 확인과 인도

대상: 기존 테스트, 작은 네이티브 통합 입력 모음, CURRENT_STATE의 실제 상태 정정.

확인 순서:

1. 코드 작성에 사용하지 않은 저장소 밖 사용자 입력으로 기본 연결을 확인한다. 확보하지 못했으면 그 항목은 미실시로 둔다. 테스트용 생성 모델로 대체해 사용자 입력 확인이라고 쓰지 않는다.
2. 압력·자중, 마찰 접촉, 비선형 재료, 사면체·육면체·셸을 포함하도록 입력을 구성한다. 가능한 조합은 한 모델로 묶되 모두를 하나의 거대 모델에 강제하지 않는다.
3. 네이티브 입력 보존·실행·결과 읽기·ParaView 전달·토론·변경·재실행·저장·재열기를 같은 프로젝트 경로로 확인한다. 각 프로그램을 따로 실행한 결과로 대체하지 않는다.
4. 수정 관련 단위/계약/통합 검사가 통과한 뒤 전체 제품 회귀 검사를 한 번 수행한다. 새 수정·실패 없이 전체 검사를 반복하지 않는다.
5. Windows 실화면은 '사용자 지시로 보류'로 별도 남긴다. 비시각적 연결이 통과해도 1단계의 모든 종료 조건이나 GUI 완료를 선언하지 않는다.

인도 시 보고할 내용은 변경된 사용자 동작, 남은 결함, 확인한 실행 환경과 입력 범위다. 기능별 수용 보고서·manifest·증거 packet을 추가하지 않는다. 실제 입력·로그·결과는 테스트 또는 프로젝트의 자연스러운 산출물로 남긴다.

## 5. 후속 확장 조건

현재 수치·PDE·설치·RAG 코드는 보존한다. 앞 단계에서 발견되는 데이터 무결성 결함은 고치되 다음 확장은 본선의 비시각적 연결이 성립한 뒤 진행한다.

- Code_Aster·OpenCourant: 등록 목록에 이름을 넣는 작업과 실제 네이티브 파일 교환·실행·판독 지원을 구분한다. 기존 GUI에 프로그램 정의와 어댑터를 붙인다.
- 최적화: 실제 열린 프로젝트의 변수와 응답을 네이티브 변경·JobManager 실행 경로에 연결한다. run_fn이 관리 경로를 우회하지 않게 한다. 기존 holdout·실제 재평가 검사는 유지한다.
- PDE: 자체 입력 형식을 유지한다. 구조 FE 공통 모델에 억지로 넣지 않는다. 제품 실행을 노출할 때 같은 작업 관리·결과 참조 계약을 사용한다.
- RAG: 매뉴얼 수와 조각 수 확대는 결과 출처·솔버 제한·오류 표시가 확보된 뒤 한다.
- Windows: 사용자가 보류를 해제하면 실제 창 연계·경로·화면 배율·입력 조작을 확인한다. 그 전에는 확인한 것으로 표시하지 않는다.

## 6. Codex 작업 방식

1. 원격 main을 새로 clone하고 SHA와 해당 경로를 확인한다. 이전 리뷰와 달라진 부분만 좁게 대조하고 저장소 전체 진단을 반복하지 않는다.
2. 현재 작업 단위의 사용자 행동과 실패 조건을 먼저 정한다. 재현 가능한 결함부터 수정한다.
3. 기존 자산을 찾고 재사용한다. 불필요한 추상화·새 자체 전처리기·고정 예제·별도 실행 소유자를 추가하지 않는다.
4. 파일 소유 규칙을 지킨다. 공유 파일과 모듈 경계 변경은 통합 담당이 일괄 반영한다. 병렬 작업을 별도로 지시받은 경우에만 독립 범위를 나누며, 같은 공유 파일을 여러 작업자가 동시에 바꾸지 않는다.
5. 관련 테스트를 실행한 뒤 PR에 문제·바뀐 행동·검증·남은 범위를 적는다. **[보고 기준 보강]** 로컬 작업 완료·원격 브랜치 게시·원격 main 반영을 구분한다. 병합 후에는 원격 main을 다시 새로 clone해 대상 파일 목록과 관련 테스트를 확인하고 그 SHA를 기록한 뒤에만 반영 완료라고 보고한다. 실제 확인이 없는 '완료' 표현을 사용하지 않는다.
6. 현재 작업 단위가 닫히면 다음 단위로 진행한다. 주변 기능을 더 만드는 일을 본선 연결 진척으로 보고하지 않는다. main 병합은 세션의 유효한 사용자 권한과 저장소 규칙을 따른다.

구현 지시를 받은 세션의 시작 문장 예시:

> DESIGN.md 맨 앞 제품 정의와 기준 결정 5가지를 최우선으로, 이 계획의 P1부터 구현하라. 현재 코드에서 이미 수정된 항목은 확인 후 건너뛰고, 남은 결함을 실제로 수정하고 관련 테스트를 수행하라. 런처·트리·도킹·아이콘 자산은 유지하고, 네이티브 파일과 실행 결과를 연결하는 본선으로 전환하라. Windows 실화면 보류를 유지하고, 구현·자동 검증·실환경 확인을 구분해서 보고하라. 이 지시는 별도로 승인된 구현 범위에 한해 적용한다.
