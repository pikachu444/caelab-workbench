# 개발 토론에서 결정한 내용 — 한국어 설명

이 문서는 앞선 개발 설계 토론의 내용을 이해하기 쉽게 풀어 쓴 설명입니다. 당시 발언을 새로 작성한 원문은 아닙니다. 각 담당자가 직접 쓴 발언과 파일 확인값은 [원래 토론 기록](debate-recovery-ascii.jsonl)에 그대로 보존합니다.

## 무엇을 두고 토론했는지

목표는 여러 재료 모델의 계수를 시험자료로 찾고, 실제 자료를 근거로 전문가 자문과 별도 검토를 받고, 외부 프로그램에서 후처리할 수 있게 하는 것입니다.

토론에서는 기능 이름이나 파일이 있다는 사실만으로 지원·검증·완료를 선언할 수 있는지부터 따졌습니다. 그 결과 계산식, 데이터 형식, 실행과 결과 읽기, 오류 처리, 저장, 화면, 완료 검사의 구체적인 조건을 고쳤습니다.

| M | 전체 범위와 공통 규칙을 합치는 담당입니다. |
| A | DP·발포체·직교이방 재료의 계산을 조사하고 명세를 작성했습니다. |

| 3 | F | 재료식의 표기, 에너지 단위, 큰 오차와 물리 제약 위반의 구분, 결과 필수 항목 검사를 지적했습니다. |
| 4 | M | 지적을 받아 공통 데이터와 저장·평가 규칙을 수정하고, 작성자들의 수정본을 다시 검토하도록 했습니다. |

| 6 | B | 다른 위치에서의 재실행, 최적화의 제약조건, 압축성 초탄성 모델의 수치해 선택을 어떻게 보완했는지 설명했습니다. |

| 8 | D | 실제 시간·체적·층·요소 ID와 변환 프로그램 호출, 원본 보존, RP 자동 열기 규칙을 고쳤다고 설명했습니다. |
| 9 | E | 수정된 파일과 실행 기록을 실제로 다시 읽고 자신이 제기한 설계 문제를 닫았습니다. 제품 기능 전체의 완료는 승인하지 않았습니다. |
| 10 | F | 수정된 식·수치·출처와 실제 실행 기록을 다시 확인하고, 명세를 구현에 넘길 수 있다고 판단했습니다. 실행하지 않은 항목은 남겨 두었습니다. |
| 11 | M | 해당 명세와 자료를 통합하고 최종 파일·링크·토론 순서 검사를 진행하기로 했습니다. 실제 제품 구현 작업은 별도로 남겼습니다. |

## 어떤 문제를 발견했고 무엇을 바꿨는지

### 1. 재료 이름만 같다고 같은 식을 쓰면 안 됩니다

DP는 구현마다 식과 부호, 경화·소성 흐름, 캡이나 인장 처리 등이 다를 수 있습니다. 사용할 구체적인 식과 계산 범위를 고정하도록 했습니다.

Xia 원모델과 다른 문헌에서 파생한 직교이방 탄소성 모델도 구분했습니다. 파생 모델을 원 Xia나 LAW112와 같은 모델이라고 표시하지 않습니다. GEOS를 이용하는 실행 경로는 Linux에서만 지원하도록 정했고, Windows에서 사용할 별도 계산 방법과 구분했습니다.

### 2. 오차가 크다는 것과 계산에 실패했다는 것은 다릅니다

정상적으로 계산했지만 시험곡선과 잘 맞지 않으면, 큰 오차를 남겨 계수를 더 조정할 수 있어야 합니다. 물리적 제약을 위반한 경우도 계산이 유효하다면 그 값과 위반 사실을 함께 남깁니다.

반면 계수 동정에 필수인 계산이 실패하거나 필요한 결과를 읽지 못하면 유효한 목적값을 만들 수 없습니다. 별도로 남겨 둔 검증시험의 불합격 때문에 정상적인 동정 오차까지 지우지 않도록 했습니다. 실패한 시험을 빼고 평균 오차를 낮추는 방식도 금지했습니다.

### 3. 화면의 필드 이름만으로 물리량을 판단하면 안 됩니다

실제 솔버를 실행하고 원문 코드를 읽으면서 다음 가정을 고쳤습니다.

- 요청한 쉘 적분점 수가 그대로 사용된다고 가정하지 않습니다. LAW1에서 실제로 적용된 설정과, 다른 LAW2 시험의 두께 방향 결과를 구분했습니다.
- 파일 번호나 요청한 출력 간격을 실제 시간으로 대신하지 않습니다. 결과파일에 기록된 시간을 읽습니다.
- 체적 출력의 오래된 설명만 믿지 않고 실제 계산 코드와 밀도·절점 변형을 대조했습니다.
- 필요한 쉘 층이 없는데 다른 층이나 막응력으로 대신하지 않습니다.
- 요소 ID, 층, 좌표계, 단위, 응력·변형률의 정의가 맞는지 확인한 뒤 수치를 비교합니다.
- 결과 변환 프로그램이 화면에 출력하는 내용과 실제 생성하는 CSV 파일을 구분하고, 정확한 실행 인자를 정했습니다.

### 4. 저장 직전 다른 작업이 파일을 바꿀 수 있습니다

계산 조건을 식별하는 값과 현재 문서 파일이 바뀌었는지 확인하는 값을 분리했습니다. 결과 목록이 갱신됐다는 이유로 계산 조건까지 달라졌다고 처리하지 않습니다.

다른 이름으로 저장할 때는 원본을 보존하고 필요한 자료와 결과를 함께 복사해야 합니다. 읽기 전용 원본에 잠금파일이나 복구 기록을 쓰지 않으며, 복사 중 오류가 나도 유효한 원본이나 완료된 복사본을 지우지 않도록 했습니다. 여러 문서가 서로의 잠금을 기다려 멈추는 순서도 피하도록 정했습니다.

### 5. 답변 일부만 검토해서 전체 답변이 통과하면 안 됩니다

AI가 스스로 골라 낸 주장만 검사하고 나머지 문장을 빠뜨리면, 근거 없는 답변도 통과할 수 있습니다. 프로그램이 답변 전체를 나눠 확인하고, 빠진 문장이나 근거 없는 주장이 있으면 충분한 검토가 아니라고 처리하도록 했습니다.

자료 형식을 엄격하게 검사한다던 예제 코드에도 우회 문제가 있었습니다. 허용하지 않은 속성, 상속된 인용 이름, JSON에서 허용하지 않는 공백, 한글 문장의 바이트 수 제한 문제를 찾아 고쳤습니다. 이는 데이터 형식 검사입니다. 실제 AI 답변의 공학적 정답률을 확인한 시험은 아닙니다.

### 6. 수정된 답변에는 수정된 검토 자료가 필요합니다

새 답변에 예전 답변의 문장 구분과 검사값을 그대로 붙인 시험자료를 발견해 고쳤습니다. 이전 지적, 수정한 답변, 그 답변이 참고한 자료를 정확히 연결하도록 했습니다.

평가 질문에도 질문의 판본과 검색 조건이 서로 다르거나, 솔버 이름이 빠진 경우가 있어 수정했습니다. 이렇게 준비한 질문과 자료가 있다는 사실만으로 실제 문헌 검색과 AI 자문 전체가 검증된 것은 아닙니다.

### 7. RP를 열었다는 사실만으로 후처리 연결이 끝나지 않습니다

기존 RP에서 폴더를 수동으로 여는 방법, Workbench가 결과를 변환하고 수치를 읽는 기능, 선택한 결과를 자동으로 열기 위한 RP 수정판을 나눴습니다.

자동 연결은 전달한 자료가 실제로 표시됐는지 확인해야 합니다. 원래 결과를 덮어쓰거나 이미 수행한 해석을 RP가 다시 실행하지 않도록 정했습니다. 새 자동 열기 명령이 현재 원래 RP에 있는 기능이라고 표시하지 않습니다.

## 검토 결과의 정확한 의미

E와 F는 자신이 지적한 문제를 수정된 파일에서 다시 확인했습니다. 최종 판단은 **선정한 범위의 개발 명세를 구현에 넘길 수 있다**는 것입니다.

작은 발포체 계산과 점탄성 계수 동정 등 일부 실제 실행은 별도로 확인했습니다. NEML 계산, 실제 AI 자문 전체, 새 재료 연구 화면, 새 Prep 적용 기능, RP 수정판, Windows와 실제 재료시험의 검증은 이 명세 검토로 완료되지 않았습니다.

명세서를 검토한 결과와 제품을 실제 사용해 검사한 결과는 계속 구분합니다. 상세 검토는 [E 보고서](review-E.md), [F 보고서](review-F.md), [자료와 실행 기록 안내](README.md)를 참고하면 됩니다.
